# Requested system fixes: release procedure

The release branch is `fix/requested-system-fixes-20261015`. It contains the requested security, account/OTP, booking/checkout, inventory/payroll/reporting, technician/project/daily-kit, and receipt fixes. Local diagnostic files, credentials, backups and the workstation's npm launcher are excluded.

The owner confirmed that updates to the deployment branch trigger Dokploy automatically. Keep the release separate from `main` until the production startup check passes. Publishing a release branch does not apply the two-project database cleanup.

## Check the current server without deploying the application

The portable preflight embeds the same secret and MongoDB configuration guards as the new application. It opens no database connection, changes no records, and prints no secret values. Its scope is startup configuration, not verification of the firewall, backups, email delivery or every application workflow.

In Dokploy's **server terminal**, download the checker from the published release branch:

```sh
curl --fail --silent --show-error --location --output /tmp/racs-release-preflight.cjs https://raw.githubusercontent.com/rinmico2-ui/racs-ready/fix/requested-system-fixes-20261015/deploy/dokploy/release-preflight.cjs
```

Find the running **web application** container; do not choose the MongoDB container:

```sh
docker ps --format '{{.ID}}  {{.Names}}  {{.Image}}'
```

Replace `WEB_CONTAINER_ID` below with that container ID:

```sh
docker cp /tmp/racs-release-preflight.cjs WEB_CONTAINER_ID:/tmp/racs-release-preflight.cjs
```

```sh
docker exec WEB_CONTAINER_ID node /tmp/racs-release-preflight.cjs
```

The result must contain `"ready": true`. Share the JSON result if assistance is needed; it contains only checks and setting names. Do not share environment values. If the checker reports missing settings, make the corrections in the **web application's Environment settings**, preserving its existing working configuration. See [the security deployment steps](dokploy-security-steps.md) for authenticated internal MongoDB, unique secrets, proxy settings and safe previous-outbox-key handling. Do not reopen a public database port to run this check.

If the GitHub repository is private and the download returns 404, copy the published `deploy/dokploy/release-preflight.cjs` from your authenticated GitHub/local checkout to the server, then use the same `docker cp` and `docker exec` steps. Do not paste an access token into the command or chat.

## Publish to the deployment branch

Once the current production configuration passes, merge the tested release to the branch configured in Dokploy (`main` in the connected Git repository). Its automatic deployment should rebuild dependencies and restart the application. Verify that the deployment succeeds and the login page opens. Local tests do not verify the server's live environment, volumes, database topology or third-party email service.

Then run the exact two-project cleanup from the newly deployed web application's terminal:

```sh
node server/scripts/archive-requested-test-projects.js
```

```sh
node server/scripts/archive-requested-test-projects.js --apply
```

These scripts target only `6acd3b47678aa45bd94a7354` and `6accb39899a4f85a0ecba22e`. Success is JSON with `"mode": "archived"` or `"mode": "already-archived"`. Keep the reported EJSON recovery backup privately off the container. Full behavior and recovery constraints are in [the cleanup instructions](requested-test-project-cleanup.md).

Allow about 30 seconds for report caches to expire, then hard-refresh the projects and Sales and Payments pages. Confirm that the two projects are absent from the active list and the report uses **Completed work less completed period refunds**. A nonpositive net-sales margin displays **Margin unavailable**. Real completed refunds are retained; they may legitimately leave a negative reporting period. Use `node server/scripts/auditProjectTestData.js` inside the deployed application for reconciliation.

## Regenerate the portable checker

If the startup guard implementations change, regenerate the portable artifact and rerun its tests:

```sh
node server/scripts/buildReleasePreflight.js
```

```sh
node --test server/tests/release-preflight.test.js
```
